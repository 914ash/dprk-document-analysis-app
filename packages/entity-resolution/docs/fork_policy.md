# Fork Policy

## Why LanceDB

LanceDB is the **only supported vector-storage backend** for this project. It was chosen because:

1. **Embedded / serverless**: No separate database process to manage. The store is a directory of Lance files that live alongside the rest of the data pipeline artifacts.
2. **Native vector search**: First-class ANN (approximate nearest-neighbour) search with cosine/dot-product metrics without requiring a separate index service.
3. **Pyarrow-native**: LanceDB reads and writes Apache Arrow tables directly, making it trivially composable with Pandas and Parquet-based intermediate storage.
4. **Open source (Apache-2.0)**: No licensing friction for sanctions-research tooling.

LanceDB is a **project dependency**, not a reference implementation. It must not be replaced with pgvector, Chroma, Qdrant, Weaviate, or any other vector store without updating `docs/architecture.md`, `docs/data_model.md`, and all tests in the same change.

## Reference Repository Policy

External repositories (e.g. example notebooks, tutorial repos, upstream LanceDB demos) may be consulted for **implementation patterns** only. No code may be copied from a reference repository without:

1. Explicit attribution in the relevant source file.
2. Confirmation that the license is compatible with this project's license.
3. A note in the relevant `AGENTS.md` or commit message explaining what was adapted and why.

Reference repositories are **not** authoritative for this project's data models, layer boundaries, or CLI contracts. Those are defined in `docs/` and `src/dprk_er/types/models.py`.

## Dependency Pinning

Dependencies are declared in `pyproject.toml` with minimum-version lower bounds. Exact pins (for reproducibility) should be captured in a `requirements.lock` generated by the build tool. Do not hard-pin versions in `pyproject.toml` unless a breaking change in a specific upstream release has been identified and documented.
